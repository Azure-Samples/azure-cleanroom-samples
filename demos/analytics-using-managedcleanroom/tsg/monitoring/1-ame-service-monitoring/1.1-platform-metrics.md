# 1.1 Platform Metrics (Azure Monitor)

## Overview

Azure Monitor automatically collects platform metrics for every AKS cluster. No code changes needed — only configuration (Diagnostic Settings + Alert Rules).

These metrics cover the **infrastructure health** of the 3 AME AKS clusters (RP, Frontend, CM). They answer: "Is the cluster healthy?" — not "Is the application working?" (that's Section 1.2 Synthetic Runners).

## Current State

**Status: Planned** — Metrics are auto-collected but no alert rules are configured yet.

## Metrics & Alert Rules

### Node-Level Metrics

| Metric | Source | Alert Threshold | Severity | Action |
|--------|--------|----------------|----------|--------|
| Node CPU % | Azure Monitor | > 80% sustained 5 min | Sev2 | Scale out or investigate workload |
| Node Memory Working Set % | Azure Monitor | > 85% sustained 5 min | Sev2 | Risk of OOM — scale out or tune requests/limits |
| Cluster Node Count | Azure Monitor | < expected node count | Sev2 | Node lost — check node pool health |

### Pod-Level Metrics

| Metric | Source | Alert Threshold | Severity | Action |
|--------|--------|----------------|----------|--------|
| Pod Restart Count | Azure Monitor | > 3 in 15 min per pod | Sev2 | CrashLoop — check logs |
| Pod Status (NotReady/Failed) | Azure Monitor | Any | Sev3 | Pod stuck or crashed |

### Control Plane Metrics

| Metric | Source | Alert Threshold | Severity | Action |
|--------|--------|----------------|----------|--------|
| API Server Request Latency | Azure Monitor | p99 > 5s | Sev2 | Control plane degraded |
| API Server Availability | Azure Monitor | < 99.9% | Sev1 | Control plane down |

## Implementation Plan

### Step 1: Enable Diagnostic Settings on Each AME AKS Cluster

For each of the 3 clusters, enable Diagnostic Settings → Log Analytics workspace:

```json
{
  "type": "Microsoft.Insights/diagnosticSettings",
  "apiVersion": "2021-05-01-preview",
  "name": "aks-diagnostics",
  "scope": "[resourceId('Microsoft.ContainerService/managedClusters', parameters('clusterName'))]",
  "properties": {
    "workspaceId": "[resourceId('Microsoft.OperationalInsights/workspaces', parameters('workspaceName'))]",
    "metrics": [
      {
        "category": "AllMetrics",
        "enabled": true,
        "retentionPolicy": {
          "enabled": true,
          "days": 90
        }
      }
    ]
  }
}
```

### Step 2: Create Alert Rules

Use Azure Monitor metric alert rules. Can be deployed via ARM template or Terraform in EV2.

Example alert rule (Node CPU):
```json
{
  "type": "Microsoft.Insights/metricAlerts",
  "apiVersion": "2018-03-01",
  "name": "aks-node-cpu-high",
  "properties": {
    "severity": 2,
    "scopes": ["[resourceId('Microsoft.ContainerService/managedClusters', parameters('clusterName'))]"],
    "evaluationFrequency": "PT1M",
    "windowSize": "PT5M",
    "criteria": {
      "odata.type": "Microsoft.Azure.Monitor.SingleResourceMultipleMetricCriteria",
      "allOf": [
        {
          "name": "NodeCPUHigh",
          "metricName": "node_cpu_usage_percentage",
          "operator": "GreaterThan",
          "threshold": 80,
          "timeAggregation": "Average"
        }
      ]
    },
    "actions": [
      {
        "actionGroupId": "[resourceId('Microsoft.Insights/actionGroups', parameters('actionGroupName'))]"
      }
    ]
  }
}
```

### Step 3: Create Action Group (Route to ICM)

```json
{
  "type": "Microsoft.Insights/actionGroups",
  "name": "accr-engineering-alerts",
  "properties": {
    "groupShortName": "ACCRAlerts",
    "enabled": true,
    "emailReceivers": [],
    "webhookReceivers": [
      {
        "name": "ICM",
        "serviceUri": "<ICM webhook endpoint>"
      }
    ]
  }
}
```
