# 1.2 Synthetic Runners (Endpoint Availability & Validation)

## Overview

Synthetic runners are automated probes that **actively call service endpoints** on a schedule to verify availability and correctness. Platform metrics (Section 1.1) tell you if the cluster is healthy — synthetic runners tell you if the **application is actually working**.

Example: All pods could be Running, CPU is fine, but the app returns 500 because Cosmos DB credentials expired. Only a synthetic runner catches that.

## Synthetic Monitors

### Endpoint Availability Probes

| Monitor | Target | Method | Auth | Frequency | Alert On |
|---------|--------|--------|------|-----------|----------|
| RP endpoint | ARM endpoint (`https://management.azure.com/subscriptions/{sub}/providers/Microsoft.CleanRoom/...`) | GET on a known collaboration resource | ARM bearer token | 5 min | Failure for > 5 min |
| Frontend endpoint | Frontend Service (`/checkConnectionsInit`) | GET | None (no auth required) | 5 min | Failure for > 5 min |
| CM endpoint | Consortium Manager health endpoint | GET | Service auth | 5 min | Failure for > 5 min |

### End-to-End Validation

| Monitor | Target | What It Does | Frequency | Alert On |
|---------|--------|-------------|-----------|----------|
| BVT (Build Verification) | Full prod deployment | Create collaboration → enableWorkload → run query → validate output → delete | Daily (scheduled) | Any step failure |
| Longhaul test | Running collaboration | Keep a collaboration alive, run periodic queries, check for resource leaks and performance degradation | Continuous | Health degradation or query failure |

## Implementation Plan

### Option A: Azure Monitor Availability Tests (Simple probes)

For basic endpoint availability, use Azure Monitor Application Insights URL ping tests:

```json
{
  "type": "Microsoft.Insights/webtests",
  "apiVersion": "2022-06-15",
  "name": "frontend-availability",
  "location": "[resourceGroup().location]",
  "properties": {
    "SyntheticMonitorId": "frontend-check",
    "Name": "Frontend Availability",
    "Enabled": true,
    "Frequency": 300,
    "Timeout": 30,
    "Kind": "ping",
    "Locations": [
      { "Id": "us-va-ash-azr" },
      { "Id": "us-ca-sjc-azr" }
    ],
    "Configuration": {
      "WebTest": "<WebTest Name='Frontend' Url='https://{frontend-endpoint}/checkConnectionsInit' />"
    }
  }
}
```

**Limitation:** URL ping tests can't handle ARM auth or multi-step workflows. Use Option B for those.

### Option B: Azure Function / Pipeline (E2E tests)

For BVT and longhaul, run the existing test suite on a schedule:

```
Scheduled Trigger (Azure DevOps Pipeline / Azure Function Timer)
    │
    ├── BVT: Run bda-bvt-auto.ps1 against PROD
    │   ├── Create collaboration
    │   ├── Enable workload
    │   ├── Run query
    │   ├── Validate output
    │   └── Delete collaboration
    │
    └── Longhaul: Periodic query on long-lived collaboration
        ├── Submit query every 30 min
        ├── Check healthState
        └── Alert on degradation
```

### Option C: Geneva Synthetic Monitors (AME Standard)

AME teams typically use Geneva Synthetic Monitors for endpoint probing. This integrates directly with ICM for alerting.

## Alert Configuration

| Monitor | Condition | Severity | ICM Routing |
|---------|-----------|----------|-------------|
| RP unavailable | Probe fails > 5 min | Sev1 | ACCR On-Call |
| Frontend unavailable | Probe fails > 5 min | Sev1 | ACCR On-Call |
| CM unavailable | Probe fails > 5 min | Sev1 | ACCR On-Call |
| BVT failure | Any step fails | Sev2 | ACCR Engineering |
| Longhaul degradation | Query failure or health != Ok | Sev3 | ACCR Engineering |

## Dependencies

- Frontend `/checkConnectionsInit` endpoint must be publicly accessible (it already is — no auth required)
- ARM endpoint needs a test subscription with a known collaboration for probing
- BVT scripts (`bda-bvt-auto.ps1`) need to be parameterized for prod
- ICM integration for alert routing
