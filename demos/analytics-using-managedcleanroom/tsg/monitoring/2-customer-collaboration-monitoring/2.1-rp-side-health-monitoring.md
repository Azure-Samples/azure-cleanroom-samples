# 2.1 RP-Side Collaboration Health Monitoring

## Overview

The RP has a `cleanroommonitoringworker` that continuously watches all customer collaboration clusters. It surfaces health via the `healthState` property on the ARM resource. This section covers enhancing that monitoring with structured telemetry.

## Current State

### Already Working (Available)

- **`healthState`** = `Ok` | `Error` with `healthIssues` array on the ARM resource
- **Pod health monitoring** across all namespaces (including `analytics`), filters out `Succeeded` pods (completed Spark jobs)
- **CCF node health** monitoring via ccf-provider, auto-triggers consortium recovery when nodes are down
- **ARM Activity Log** — automatic for all CRUD operations on Collaborations, Consortiums, moboBrokers

### Needs Work (Planned)

- **Provisioning lifecycle telemetry** — per-task duration and success/failure metrics
- **Structured log correlation** — linking ARM operationId to internal workflow tasks

## 2.1.1 Health State Monitoring (Existing)

The monitoring worker checks:

| Check | What It Does | Recovery |
|-------|-------------|----------|
| Pod health (all namespaces) | Monitors pods in `analytics`, `cleanroom-system`, `telemetry` | Sets `healthState=Error` with details in `healthIssues` |
| CCF node health | Checks CCF consortium nodes via ccf-provider | Auto-triggers consortium recovery (node restart/replace) |
| Spark job status | Filters `Succeeded` pods (completed Spark jobs) from health checks | Prevents false alerts from completed batch pods |

Customer sees this via:
```bash
az rest --method GET \
  --uri "/subscriptions/{sub}/resourceGroups/{rg}/providers/Microsoft.CleanRoom/collaborations/{name}?api-version=2026-04-30-preview"
```

Response includes:
```json
{
  "properties": {
    "healthState": "Error",
    "healthIssues": [
      {
        "kind": "PodFailure",
        "namespace": "analytics",
        "podName": "spark-driver-xyz",
        "containerName": "spark",
        "reason": "OOMKilled",
        "message": "Container exceeded memory limit"
      }
    ]
  }
}
```

## 2.1.2 Provisioning Lifecycle Telemetry (Planned)

Track every workflow task with structured metrics and logs (feeds into Geneva → Kusto).

### Workflow: CreateCollaboration (~30-35 min total)

| Task | Typical Duration | What Can Go Wrong |
|------|-----------------|-------------------|
| `CreateCollaborationPreflight` | ~1 min | Validation failures (quota, region, subscription) |
| `CreateManagedResourceGroup` | ~2-5 min | MOBO InternalError (intermittent, has recovery handler) |
| `CreateCluster` | ~15 min | AKS provisioning failure, quota exceeded |
| `UpdateClusterDenyAssignments` | ~1 min | RBAC propagation delay |
| `EnableClusterObservability` | ~6 min | Prometheus/Grafana deploy failure |
| `CreateConsortium` | ~15 min | CACI capacity shortage, SEV-SNP attestation failure |
| `PrepareConsortium` | ~2 min | Null endpoints (fixed — now checks provisioningState) |
| `AddMembershipMapping` | ~1 min | Cosmos DB throttling |
| `CreateCollaborationFinalize` | ~1 min | — |

### Workflow: EnableWorkload (~8-10 min total)

| Task | Typical Duration | What Can Go Wrong |
|------|-----------------|-------------------|
| `EnableWorkloadPreflight` | ~1 min | Validation failures |
| `GenerateContract` | ~1 min | Contract generation failure |
| `CreateSparkService` | ~5 min | CACI capacity, image pull failure |
| `UpdateWorkloadNsgRules` | ~1 min | NRMS NSG conflict (has AllowInternetInboundHttps fix) |
| `SetDeploymentInfo` | ~1 min | — |
| `EnableWorkloadFinalize` | ~1 min | — |

### Metrics to Emit

```csharp
// Per-task metrics (see Section 1.3.1 for implementation pattern)
AccrMetrics.RecordTaskDuration(taskName, workflowName, durationMs, result);
AccrMetrics.RecordTaskSuccess(taskName, workflowName, region);
AccrMetrics.RecordTaskFailure(taskName, workflowName, region, exceptionType);
```

### Key Alert Thresholds

| Condition | Threshold | Action |
|-----------|----------|--------|
| CreateCollaboration P95 duration | > 45 min (normal ~30 min) | Investigate slow task |
| CreateCollaboration failure rate | > 10% in 1 hour | Check by region + task |
| EnableWorkload failure rate | > 10% in 1 hour | Check CACI capacity |
| Any task stuck | > 2x typical duration | Check for deadlock/hang |

## 2.1.3 ARM Resource Monitoring (Available — Automatic)

Azure Activity Log automatically captures:

| Resource Group | Resources | What Activity Log Shows |
|---------------|-----------|------------------------|
| Customer RG | `Microsoft.CleanRoom/Collaborations`, `Microsoft.CleanRoom/Consortiums`, `Microsoft.Resources/moboBrokers` (×2) | ARM CRUD operations, provisioning failures |
| Collab MRG (`CleanRoom_Collaborations_{name}`) | AKS cluster, VNet, Public IP, NAT Gateway, UAMI, Private DNS | Sub-resource provisioning status |
| Consortium MRG (`CleanRoom_consortiums_ccf-{name}`) | CACI container groups (×3), Storage Account, UAMI, Key Vault | CCF node deployment status |

**Note:** Deny assignments on MRGs allow `*/read`, so Activity Log (`Microsoft.Insights/eventtypes/values/read`) is accessible to customers.
