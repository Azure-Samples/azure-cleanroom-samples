# 2.2 Customer-Facing Monitoring

## Overview

What customers can see and do to monitor their own collaborations. Two API surfaces: ARM (RP) and Frontend Service.

## Current State

**Status: Mostly Available** — APIs exist but no portal experience.

## 2.2.1 RP (ARM) APIs

| API | Purpose | How Customers Use It | Status |
|-----|---------|---------------------|--------|
| `GET .../collaborations/{name}` → `properties.healthState` | Health alerting | Poll on schedule (Logic App, Azure Function), alert when `healthState != Ok` | Available |
| `POST .../collaborations/{name}/getReadonlyKubeConfig` | Cluster access | Returns readonly kubeconfig for the collaboration AKS cluster. Customer can `kubectl get pods -A`, inspect logs, port-forward to Grafana | Available |

### Example: Customer Health Monitoring with Logic App

```
Timer Trigger (every 5 min)
  → HTTP GET: /subscriptions/{sub}/resourceGroups/{rg}/providers/Microsoft.CleanRoom/collaborations/{name}
  → Condition: properties.healthState != "Ok"
    → Yes: Send email/Teams notification with healthIssues details
```

### Example: Customer Debugging with Readonly Kubeconfig

```bash
# Get readonly kubeconfig
az rest --method POST \
  --uri "/subscriptions/{sub}/resourceGroups/{rg}/providers/Microsoft.CleanRoom/collaborations/{name}/getReadonlyKubeConfig?api-version=2024-07-01" \
  --output-file collab-kubeconfig

# Inspect pods
kubectl --kubeconfig collab-kubeconfig get pods -A

# Check Spark job logs
kubectl --kubeconfig collab-kubeconfig logs spark-driver-xyz -n analytics

# Port-forward to Grafana dashboards
kubectl --kubeconfig collab-kubeconfig port-forward svc/cleanroom-spark-grafana 3000:80 -n telemetry
# Open http://localhost:3000 → Spark execution dashboards
```

## 2.2.2 Frontend Service APIs

> **Note:** The Frontend Service is a separate HTTPS endpoint — NOT an ARM endpoint. Azure Monitor does not track Frontend API calls. Customers must implement their own monitoring on these APIs.

| API | Purpose | What It Returns | Status |
|-----|---------|----------------|--------|
| `GET /collaborations/{id}` | Collaboration status | User-level collaboration status | Available |
| `GET /{collabId}/analytics/runs/{jobId}` | Query execution state | `SUBMITTED` → `RUNNING` → `COMPLETED` (or `FAILED`) | Available |
| `GET /{collabId}/analytics/queries/{name}/runs` | Run history | Total rows read/written, duration per run | Available |
| `GET /{collabId}/analytics/auditevents` | Audit trail | CCF ledger events (who did what, when) | Available |

### Example: Customer Query Monitoring

```python
import requests, time

def wait_for_query(frontend_url, collab_id, job_id, token):
    while True:
        resp = requests.get(
            f"{frontend_url}/{collab_id}/analytics/runs/{job_id}",
            headers={"Authorization": f"Bearer {token}"}
        )
        state = resp.json()["state"]
        if state == "COMPLETED":
            return resp.json()
        elif state in ("FAILED", "SUBMISSION_FAILED"):
            raise Exception(f"Query failed: {resp.json()}")
        time.sleep(30)  # Poll every 30s
```

## Gaps for Customers

| Gap | What's Missing | Priority | Status |
|-----|---------------|----------|--------|
| No portal experience | Azure Portal Insights blade for Collaborations (like AKS has) | Medium | TBD |
| No Azure Monitor metrics on Collaboration resource | Can't create metric alerts in Azure Monitor | Medium | TBD (Section 3.2) |
| No resource logs (Diagnostic Settings) on Collaboration resource | Can't route events to Log Analytics | Medium | Planned (Section 3.2) |
| No push notifications | Customer must poll — no webhooks/Event Grid | Low | Not Planned |
| Frontend API monitoring | Azure Monitor doesn't track Frontend calls | Low | By design (not ARM) |

## Future: Customer-Facing Resource Logs

When implemented (Section 3.2), customers will be able to enable Diagnostic Settings on their `Microsoft.CleanRoom/Collaborations` resource and route to their own Log Analytics workspace:

| Log Category | Events |
|-------------|--------|
| `CollaborationOperations` | Create, delete, enableWorkload, addCollaborator |
| `QueryExecution` | Query submit, state changes, completion/failure |
| `AuditEvents` | CCF ledger events |
| `HealthEvents` | Health state changes with details |

## Dependencies

- ARM resource provider support for custom metrics (for portal experience)
- Resource log (Diagnostic Settings) implementation in RP
- Frontend Service telemetry for PG-side tracking (Section 1.3.1)
