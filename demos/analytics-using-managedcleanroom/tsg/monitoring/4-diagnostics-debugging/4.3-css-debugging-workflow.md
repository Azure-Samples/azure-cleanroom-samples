# 4.3 CSS Debugging Workflow

## Overview

Step-by-step guide for CSS (Customer Support Services) engineers to triage ACCR issues without escalating to engineering. CSS has access to Azure Portal + Kusto (via security group).

## CSS Triage Steps

### Step 1: Check Collaboration Resource in Azure Portal

```
Azure Portal → Subscriptions → {customer sub} → Resource Groups → {customer RG}
  → Microsoft.CleanRoom/Collaborations/{name}
    → Properties:
       provisioningState: Succeeded | Provisioning | Failed | Deleting
       healthState: Ok | Error
       healthIssues: [ ... ]
```

| provisioningState | healthState | Meaning | Action |
|-------------------|-------------|---------|--------|
| Succeeded | Ok | Everything working | Check customer's specific complaint |
| Succeeded | Error | Cluster up but pods unhealthy | Check healthIssues details |
| Provisioning | — | Still creating (normal: 25-35 min) | Wait if < 45 min, escalate if > 60 min |
| Failed | — | Creation failed | Check Activity Log for error |
| Deleting | — | Being deleted (normal: 5-10 min) | Wait |

### Step 2: Check Activity Log

```
Azure Portal → Resource Group → Activity Log
  → Filter: Resource type = Microsoft.CleanRoom/*
  → Look for: Failed operations, error messages
```

Common Activity Log errors:

| Error | Meaning | Customer Action |
|-------|---------|----------------|
| `QuotaExceeded` | Not enough compute quota | Request quota increase for the region |
| `InternalError` on MOBO | Intermittent MOBO failure | Usually auto-recovers; wait 10 min and retry |
| `Forbidden` on role assignment | RBAC propagation delay | Wait 5 min and retry |
| `CapacityError` on CACI | No CACI capacity in region | Try a different region |

### Step 3: Check Customer TSG Issue Matrix

Reference: [Customer TSG](https://github.com/Azure-Samples/azure-cleanroom-samples/blob/managed/demos/analytics-using-managedcleanroom/tsg/customer/index.md)

Map the customer's symptom to a known issue (#1-23). Each issue has:
- Symptoms
- Root cause
- Resolution steps
- Whether engineering escalation is needed

### Step 4: Query Kusto (If Needed)

CSS engineers in the ACCR-CSS security group can query the engineering Kusto:

```kql
// Quick status check for a customer
CleanRoomOperations
| where SubscriptionId == "{customer-sub}"
| where CollaborationName == "{collab-name}"
| where Timestamp > ago(24h)
| project Timestamp, TaskName, Level, Message
| order by Timestamp desc
| take 50
```

```kql
// Check if this is a regional issue (not just this customer)
CleanRoomOperations
| where Timestamp > ago(1h)
| where Level == "Error"
| summarize FailCount=count(), AffectedCollabs=dcount(CollaborationName) by Region, TaskName
| where FailCount > 3
| order by FailCount desc
```

### Step 5: Escalate to Engineering

If Steps 1-4 don't resolve the issue, escalate with:

| Information | Where to Find It | Why Engineering Needs It |
|-------------|-----------------|------------------------|
| `subscriptionId` | ARM resource | Identify customer tenant |
| `collaborationName` | ARM resource | Find in Kusto |
| `operationId` | Activity Log | Correlate across services |
| Timeframe | Customer report | Narrow Kusto query window |
| Error message | Activity Log or healthIssues | Root cause identification |

Escalation template:
```
Subject: ACCR Issue - {collaborationName} in {region}
SubscriptionId: {sub}
CollaborationName: {name}
OperationId: {opId}
Timeframe: {when it started}
Symptom: {what the customer sees}
Activity Log Error: {error if any}
Kusto Query Link: {link to relevant query}
```

## Common CSS Scenarios

### Scenario: "My collaboration is stuck creating"

1. Check `provisioningState` → if `Provisioning` for < 45 min, it's normal
2. If > 60 min, check Activity Log for failures
3. Query Kusto for the last running task
4. If `CreateCluster` or `CreateConsortium` — these are the longest tasks (~15 min each)
5. If stuck on `CreateManagedResourceGroup` — possible MOBO issue, check if MRG exists
6. Escalate if stuck > 90 min with no progress

### Scenario: "My query failed"

1. Check Frontend API: `GET /{collabId}/analytics/runs/{jobId}` → look at `state` and error details
2. If `SUBMISSION_FAILED` — check CACI capacity, analytics namespace pods
3. If `FAILED` — check Spark driver logs via readonly kubeconfig
4. If `RUNNING` for > expected time — check Grafana for execution progress

### Scenario: "Health state is Error"

1. Check `healthIssues` array in ARM resource
2. Common issues: pod OOMKilled, pod CrashLoop, CCF node down
3. For CCF issues — auto-recovery should handle; wait 10 min
4. For persistent pod failures — escalate to engineering
