# 6.1 Existing Self-Recovery Patterns

## Overview

ACCR already has several self-recovery mechanisms built into the RP Worker and Consortium Manager. These handle known transient failures without human intervention.

## Current Recovery Patterns

### 1. Consortium Auto-Recovery

| | |
|---|---|
| **Trigger** | CCF node health check fails |
| **Action** | Automatic CCF node restart/replacement |
| **Component** | Consortium Manager + ccf-provider-client |
| **Status** | Available ✅ |

The monitoring worker continuously checks CCF node health. When a node is down, it triggers the consortium recovery workflow which restarts or replaces the failed CACI container group.

### 2. MOBO Failure Recovery Handler

| | |
|---|---|
| **Trigger** | `CreateManagedResourceGroup` task fails with MOBO `InternalError` |
| **Action** | Check if MRG already exists; if yes, skip creation and proceed |
| **Component** | RP Worker |
| **Status** | Available ✅ |

MOBO (Managed-On-Behalf-Of) has intermittent failures. The recovery handler detects that the MRG was actually created despite the error response, and continues the workflow.

### 3. Retry on HTTP 403 (RBAC Propagation)

| | |
|---|---|
| **Trigger** | 403 Forbidden on role assignment or resource access |
| **Action** | Retry up to 12 times, 15 seconds apart (3 minutes total) |
| **Component** | RP Worker (`WaitForRbacPropagation`) |
| **Status** | Available ✅ |

Azure RBAC is eventually consistent. After creating role assignments, the RP waits for propagation by retrying operations that return 403. Checks all 3 required roles before proceeding.

### 4. Retry on Cosmos DB Transient Errors

| | |
|---|---|
| **Trigger** | Cosmos DB returns 408 (Timeout), 429 (Throttled), or 503 (Service Unavailable) |
| **Action** | Automatic retry with built-in Cosmos SDK retry policy |
| **Component** | RP Worker (all Cosmos operations) |
| **Status** | Available ✅ |

The Cosmos DB SDK handles transient errors automatically with exponential backoff.

## Recovery Pattern Summary

| Pattern | Failure Type | Recovery Time | Success Rate |
|---------|-------------|---------------|-------------|
| Consortium auto-recovery | CCF node failure | 2-5 min | High |
| MOBO recovery | MOBO InternalError | Immediate (skip) | High |
| RBAC retry | Azure RBAC propagation | 15s - 3 min | Very High (usually succeeds within 2-3 retries) |
| Cosmos retry | Cosmos transient errors | < 30s | Very High |

## Monitoring Recovery Actions

Once structured logging is in place (Section 1.3.2), track recovery events:

```kql
// Recovery events in last 24h
CleanRoomOperations
| where Timestamp > ago(24h)
| where TaskName in ("ConsortiumRecovery", "MoboRecovery", "WaitForRbacPropagation", "CosmosRetry")
| summarize Count=count(), SuccessRate=round(100.0 * countif(Level == "Information") / count(), 1) by TaskName
| order by Count desc

// If recovery success rate drops, it indicates a systemic issue
```
